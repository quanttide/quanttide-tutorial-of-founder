# UI 和 UX 的分界

## 为什么要把一件事拆成两面

评价一个界面的时候，最容易发生的事是把两件不同的问题混在一起说。

「这个界面很乱」——是东西摆得乱，还是用起来绕？说的人自己也未必分得清，于是改的时候常常改错地方：该删的标签没删，该合并的步骤没合。

分成两面之后，每句话都有地方放，改的人也知道该动哪里。

## 两面各自是什么

**UI 是界面这个物件。** 它显示什么、怎么显示、摆在哪、字多大，以及四种状态——空、加载、错误、成功——齐不齐。一句话：把它截图下来，你还能判断的那些，都是 UI。

**UX 是走完一遍的过程。** 从打开到拿到结果，中间经过几步、有没有卡住、错了能不能回来、换台机器还行不行。一句话：必须亲手操作才能判断的，都是 UX。

截图判 UI，操作判 UX——这就是分界判据的由来。它不是学术定义，是为了让两个人评分时能落到同一边。

## 同一个问题只记一次

同一个问题常常两面都能记一笔。

比如「报错只有一行字，没说怎么办」。它既是 UI 的问题（错误状态没显示全），也是 UX 的问题（出错之后没有恢复路径）。两面各扣一次，同一个毛病被罚两遍，分数反映的就是条文写重了，不是产品差两倍。

所以规矩是：按**主责面**记一次，另一面不再记。

## 几处容易记错的

**「界面很丑」不计分。** [章程](../../bylaw/design/usability.md)不设美观维度：观感不影响任务完成就不进分数。真正进分数的是「因为排布，我不知道该点哪」——那是信息层级。

**「流程太长」是 UX，但步数多本身不扣分。** 扣分的是每一步都要重新想「我现在在哪、接下来干嘛」。[《六条判据为什么这样写》](usability-rules-explained.md)里任务闭环要求「步数最少」，指的正是这类能砍掉的重复定位——能一步到位却要绕五步，才算没做到最少。

**「看不懂术语」两边都沾。** 界面上写着编译开关的名字，是 UI 的文本问题；它导致人不敢往下点，是 UX 的发现障碍。按主责面记 UI（那行文本本来就不该出现），UX 不重复记。

## 第一次怎么走

拿到一个界面，先截图，把截图能回答的问题答完：四种状态齐不齐，一屏有没有一个明显的下一步，文字里有没有外行看不懂的词。

答完再动手走一遍：从头到尾记步数，试着回一次源头，故意走错一次看能不能回来。

两遍分开做。别在走的过程中顺手评判摆设，也别在截图的时候脑补流程会怎么走。
